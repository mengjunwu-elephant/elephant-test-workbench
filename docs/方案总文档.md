### 一、整改基线与计数口径

本轮只读核对本项目迁移资产：456份现有定义、3232组参数，其中14份只读已转换，442份待完善覆盖3218组参数。待完善按原工作簿分布：Pro450本体80份/670组，P1本体63份/295组，280本体52份/511组，E1本体89份/761组，Mercury双臂73份/577组，pro_gripper28份/81组，Mercury夹爪16份/55组，Mercury灵巧手28份/228组，P1附件13份/40组。14份已有转换也参加语义回归，不因当前启用而免检。

这些数量是原工作表聚合条目，不是独立测试函数或最终执行实例数。一张表关联多个测试函数时应按真实场景拆分；因此整改后的定义数量可以变化，覆盖率按原始来源映射核对，不能只追求442个条目消失。

另外514份来源测试文本中有46份未被当前456份定义引用。它们已在来源清单中保留，须逐项确认是漏绑定、缺数据、重复/过时场景还是独立测试，再归入对应批次或保留有依据的处置记录，不能仅凭未绑定认定无用，也不臆造缺失参数。

manifest 的 conversion_limits 是保守转换器的“首个不支持原因”，不是每条用例的完整缺陷：例如多函数、双臂和fixture可能同时存在。整改需逐例核对，不能按该计数直接认定对应用例本身有错。静态统计也只能发现源码特征，不能证明其在实际设备上的行为。

### 二、逐例整改台账与完成条件

台账归入本项目用例迁移元数据和统一汇总，记录原条目ID、原工作簿/sheet/行号、关联源文件/测试函数/参数过滤、目标新用例ID、拆分/合并映射、适用主机/附件/SDK、问题清单、整改批次、转换版本、静态/自动检查证据、阻断原因、实机验收记录。一个原条目拆成多条后，映射仍须可追溯。

每条核对：前置条件、全部动作及顺序、数据组过滤和类型、正常/边界/预期异常、断言类型/值/容差、人工参与、条件分支与等待、fixture恢复和恢复验证。缺项必须有明确解释和依据；删除重复/过时场景应保留原记录、理由及承接关系。能力不足或依据不足仍登记为未解决阻断，不算转换完成。

定义整改完成需同时具备：原数据/场景覆盖对账通过、实际步骤已取代review占位、没有旧工程运行依赖、相关SDK与公共方法需求明确、断言与恢复语义核对通过、静态检查和有意义的tests替身回归通过。只有实机证据满足约定条件后才登记“实机验收通过”；转换完成本身不生成通过结果。

### 三、分层处理方法

- **P0 来源与语义**：为全部442份及46份未绑定来源建立映射。优先保留多函数的test_type过滤、同参数不同模式和数据覆盖，不把整张表强塞进单一固定流程；保留原 == / isinstance 与异常语义，不改变负向输入类型。旧硬编码期望如固件版本需核对规格或已确认矩阵，不能为了通过而降低断言。
- **P0 前置与恢复**：明确恢复到原值还是指定基准，按原fixture与当前适配要求补齐动作、等待和实际读回验证；恢复失败停止后续任务。运动、点动、上电、夹爪/灵巧手动作及双臂必须记录操作范围和停止条件，缺少必要恢复或验证依据保持阻断。单例内部前置/恢复继续由用例负责，不把它们隐藏到测试计划中。
- **P1 复杂流程**：仅依赖已知参数的分支可按参数场景展开；依赖实机读回的分支、轮询或复杂动作使用有界步骤/已注册公共方法表达。确需扩展引擎时先定义最小能力和边界，再为真实场景实现与验证，不执行旧Python文本或提供任意脚本入口。eval类输入仅安全解析允许的字面量；JSON无法表达的特殊值需明确的有类型表示与解码规则，未支持时阻断，不将其改成正常值。
- **P1 机型与附件适配**：双臂区分左右通道并保持串行协调；附件按实际宿主、连接方式及SDK支持拆分。当前 pro_gripper 工作簿聚合了不同宿主的来源，不能直接认为28份全部属于450；仅修改model字段或复用主臂运动读回不等于完成附件适配。
- **P1 人工与异常**：保留提示内容、可接受答案、超时和拒绝后的恢复；预期异常核对实际SDK异常类型和触发条件，不将任意异常当通过。循环/等待均有上限和取消检查，避免现场挂起。
- **P2 使用与文档**：库中按具体阻断原因筛选；显示原/新用例映射和版本差异；可将已完整转换的定义加入测试计划。跨用例共享未恢复状态或变量的场景，优先改为具备完整生命周期的一条场景用例，不能用排序掩盖隐含依赖。

## 2026-11-13：三模块职责重新设计（设计定稿，未实施）

用户已回答三个收敛问题，并回复“确认执行”。本轮确认范围是输出设计，不是修改产品代码。下述内容是目标设计，现有产品仍为 0.4.0；没有据此新增页面、数据库结构或设备操作。

### 一、第一性原理：三类对象，各有一个归属

- **用例库管理 Case：定义一次检查怎样判定正确。** 包含前置、动作、读取、断言、参数组和恢复，单例编辑器内置在库中。
- **用例编排管理 TestPlan：定义哪些用例按什么次序组合。** 引用已有用例版本，管理顺序、选定数据组、参数覆盖、重复次数及失败策略，可保存、复用并随源码 Git 同步。
- **测试执行管理 Run：定义本次使用什么设备和环境，并记录实际发生的过程。** 统一进行运行配置、预检、开始、暂停/停止、人工确认与监控；启动时固化计划和用例快照。

同一份 Case 可以被多个计划引用；一个计划可以多次运行；每次 Run 有独立配置、证据和结果。编辑 Case 或 Plan 不改写已经启动的 Run。全局设备会话独立存在，任务完成不自动断开会话。

```mermaid
flowchart LR
    A[用例库：单例定义与版本] -->|选择已有用例| B[用例编排：保存测试计划]
    A -->|单例试跑 / 临时批量| C[测试执行：本次运行配置]
    B -->|带入计划| C
    C -->|预检与实机确认| D[冻结快照并启动]
    D --> E[运行监控：日志、断言、恢复]
    E --> F[报告中心：历史证据与比较]
```

### 二、用例库：找到、写好、管理一条用例

**主要操作**：检索筛选、查看、新建、编辑、复制、归档、启用/停用、查看来源/版本差异、加入计划、准备试跑。已被计划引用的用例归档时保留其被引用版本，不做级联删除。

**页面布局**：顶部是搜索、机型、分类和可用性筛选；中部是用例列表及启用状态、保存版本、Git 同步状态、最近实测结果；侧栏或详情页显示说明、参数、步骤、恢复与版本。通过“编辑用例”打开库内编辑工作区，保留现有三栏步骤编辑器：步骤库 / 有序步骤 / 参数配置。复杂编辑可全屏，顶部仍显示“用例库 / 用例名”，不占用多用例编排模块。

**Git 与迁移**：Git 同步移至“版本与同步”页签或折叠面板；迁移来源与待完善说明位于对应用例详情，默认列表以测试人员找用例为中心。“保存用例”写入本机定义并生成版本；“写回文件 / 提交 / 推送”分别显示进度，不把保存等同于团队同步。

**操作流**：编辑 → 校验并保存 → 可选准备试跑 / 加入计划。存在未保存修改时，试跑入口先提示保存或取消，不发送任意未保存 inline_cases。“准备试跑”只带入测试执行，不直接连接设备或启动任务。用例库不配置实际串口/IP，不展示全局连接为单例运行结果。

### 三、用例编排：组合一份可复用的测试计划

**主要操作**：新建/复制/保存/归档计划，从库中选例，调整顺序，设置条目名称、参数组、覆盖参数、重复次数和失败策略，查看引用变化，准备运行。顶部以计划列表或计划切换器进入编辑；“用例编排”页面副标题明确为“测试计划”。

**编辑布局**：左侧为当前机型可选用例；中间为计划条目顺序；右侧为选中条目的版本、参数组及参数覆盖。默认筛选可执行用例；允许查看/引用待完善条目以组织工作，但计划显示阻断原因，不能启动。每个条目有独立 item_id，同一用例可以以不同参数重复加入，拖动顺序必须原样执行。

**计划粒度**：第一阶段仅支持有序串行条目、重复、参数化和失败策略，不增加任意 Python、分支图、递归嵌套计划或同设备并行。计划不内联修改用例步骤/断言/恢复；若要改逻辑，打开用例库编辑并显式更新计划引用。条目参数覆盖仅覆盖用例已声明的可覆盖参数，保留 JSON 类型；不悄悄改变负向参数、目标值或容差。

**恢复与依赖**：每条用例仍拥有自己的前置/恢复。跨用例变量和未恢复状态不作为隐含依赖；确实需要连续设备状态的场景，应在一条完整场景用例内表达。普通失败仅在恢复完成且状态可确认时按计划选择继续或停止；恢复失败、状态未知始终终止后续条目，计划不能绕过该规则。

**参数层次**：用例默认值 → 所选数据组 → 计划条目覆盖 → 本次运行中显式允许的覆盖。启动前呈现最终有效参数；Run 保存每层来源和最终值，不将运行参数写回 Case 或 Plan。

### 四、测试执行：配置一次运行并观察真实过程

页面分为 **待运行配置** 和 **运行监控**，不再是只能从别处进入的日志页。

**待运行配置**：可从用例库、计划页带入选择，也可直接选已保存用例/计划。显示当前机型与实际连接目标摘要、所选 SDK、计划/用例版本、参数组、最终顺序与预计执行实例数。设备配置继续由设备管理维护；此处选择或确认本项目当前设备配置，不引入工位编号或把 IP/串口写进计划。

**静态预检**：检查用例完整性与启用状态、迁移待完善步骤、机型一致性、SDK/公共方法版本、计划引用是否可解析、数据组与参数合法性、当前设备占用及连接读回质量。预检不得发送运动、上电或其他控制指令；设备版本只使用当前会话已采集证据。缺连接时引导使用全局连接入口，连接本身按现有规则建立和校验。

**开始运行**：用户确认本次目标和现场范围后，服务端在调度锁内重新检查版本、参数、占用和实际连接条件，再原子固化快照并启动；前端预检后发生版本变化时拒绝启动并要求重新核对，不静默使用新内容。保存运行配置不会提前占用设备或自动启动。

**运行监控布局**：顶部为任务状态、设备、来源版本和进度；左侧为用例/数据组/重复条目的执行树；中部为当前步骤、有效遥测及日志；右侧为原始返回、断言、人工确认和恢复。可筛选日志、请求暂停/继续/停止；暂停在当前用例及恢复完成后的边界生效，不在动作或恢复中间截停。停止会结束后续条目并按执行端规则处理当前恢复，进程终止不代表设备物理停止。

**完成与重跑**：任务结束后保留该次结果和历史快照，明确“任务已结束”；全局连接状态独立显示，保持会话供继续使用。修改运行参数或重跑均创建新 Run，不改写旧结果。结果聚合区分逻辑用例数、数据组/重复展开后的实例数，以及通过/失败/跳过/未执行/中断，不能把未执行计作通过。

**任务范围**：测试执行展示用例、计划及专项测试运行；连接会话和单次接口调试不进入测试运行选择器。接口调试继续本页持续连接、直接调用和展示日志。响应时间/老化页面保留各自的场景与指标配置职责，其测试入口后续接入同一运行配置/监控流程；报告中心负责历史检索、完整证据导出与比较，不重复编辑用例。

### 五、版本与状态：定义、同步、执行分别显示

**Case** 至少保存稳定 ID、定义修订号、内容哈希、机型、步骤、参数/数据组、适用 SDK/公共方法条件、启用状态与迁移来源。可执行性以“待完善 / 已校验但未启用 / 已启用 / 已停用或归档”等明确含义展示；结构检查通过、人工启用、实机验收通过是三种不同证据，不能相互替代。

**TestPlan** 保存稳定 ID、名称、机型、计划版本、独立 item_id 的有序列表、每项引用的 Case ID/修订号/内容哈希、所选数据组、参数覆盖、重复与失败策略。引用固定版本，不自动追随最新。保存计划时一并固化引用定义快照（按内容哈希去重），随计划文件共享，保证旧版本在另一个工作区也可解析；新用例版本只显示“可更新”，由用户明确查看差异并更新计划引用。当前停用/归档限制仍在预检重新检查，不因持有旧快照而绕过禁用要求。

**Run** 保存运行 ID、源 Case/Plan 标识、保存版本、完整解析定义快照、条目顺序与最终参数、Git HEAD/资产哈希/相关文件修改状态、设备和 SDK/固件快照、状态、原始事件与恢复证据。重复引用通过 item_id、数据组索引（相对于固定内容哈希）、重复序号和步骤 ID 定位，避免同一用例多次运行的日志混在一起。

**Git 状态独立**：本机未写回、文件未提交、已提交待推送、已同步不能混成“草稿/正式”一个字段。允许已保存且满足执行条件的本机草稿试跑；结果标记“本地草稿”，记录其内容哈希与相关文件状态。即使仓库存在 HEAD，未提交草稿也不得标为“执行该 commit 的版本”。用户选择 Git 版本运行时，必须使用相应定义快照且完整记录该提交；推送状态不等于实机验证通过。

Case 与 Plan 定义随本项目源码 Git 管理；运行配置中的设备地址、连接环境及所有结果留在本机。计划 JSON 不包含设备 IP/串口、账号或运行结果；只保存其依赖要求。写回/拉取仍使用冲突保护，运行快照不随 Git 操作变化。

### 七、验收标准与示例

1. 在用例库编辑并保存 A、B；加入计划 P 为 A → B → A，重复 A 可以使用不同参数，重开页面后顺序及参数仍存在。

3. 运行 P 严格按 A → B → A 展开，结果能区分两个 A；计划内容不能被数据库返回顺序改变。
4. 修改 A 产生新版本，P 仍引用原版并提示可更新；更新引用前展示差异。跨工作区通过 Git 载入 P 能还原其固定引用；当前禁用或待完善用例在启动时仍被阻断。
5. 未提交但已保存的 A 可以试跑，报告明确本地草稿和实际内容哈希；未保存更改必须先保存，不能借用旧 Git SHA 冒充已提交版本。

7. 普通失败且恢复成功时按计划策略处理；恢复失败或状态未知时始终停止。暂停等待当前用例和恢复边界，停止超时不能显示设备已停止。
8. 测试结束后全局连接仍有效时继续显示有效连接，接口调试仍可在本页使用；历史遥测不能被标为当前读回。

## 四、连接与失败语义

保存只是配置。450 使用 IP 与 TCP 端口（默认 4500），不使用波特率。连接执行器验证实际位置与运动状态，校验通过后保持 SDK 连接，每 0.5 秒继续读取；接口/用例任务排入同一执行器，避免二次建连和自锁。

右上角显示已连接、已断开以及连接/断开中的过渡状态，并提供连接/断开操作。有效状态必须来自当前连接的近期读回；遥测过期或异常立即失效，不用配置或历史成功冒充在线。断开须等待正在执行的任务先停止并恢复；连接关闭后释放占用，状态未知则隔离。

450 TCP 连接有可配置超时，默认 8 秒；首次校验/进程启动有独立兜底。Windows 的 venv 启动器及其真实子进程按进程树清理，不能只结束启动器。连接失败尚未建立 TCP 时明确失败并释放；通信已经建立但状态未知时保留隔离。旧隔离不盲目清除。


按实际目标和 TCP 端口占用本机串口/IP，双臂占用两端口，换机型不能绕过占用。普通失败先恢复，恢复成功继续；恢复失败、状态未知或失败无恢复时阻断并隔离。人工确认不自动放行。停止超时终止进程不代表设备停止。浏览器断开不结束任务；应用重启标记中断，不自动恢复运动。跨电脑控制同一设备仍需指定唯一控制端。
